# Testing Cozy Cat Café

To run the tests, open a terminal in this folder and type `node --test`. You need Node 18 or newer, and you don't need to install anything else. Node finds every file that ends in `.test.js` and runs it. If everything is fine, the last lines say `pass 12` and `fail 0`. The same command also runs on GitHub every time someone pushes or opens a pull request, so a red ✗ next to a commit on GitHub means a test broke. Click the ✗ to see which one.

The tests focus on the three rules that decide hunger and money in the game. A cat counts as hungry when its fullness is below 30. Refilling food costs 10 coins and gives every cat 30 more fullness, but never more than 100. A customer pays 20 coins, plus 5 for every cat at fullness 30 or above. I moved these rules into `rules.js` as small functions that take numbers and give back an answer. They don't touch the screen or the game state, so they're easy to test, and that's what `rules.test.js` does.

Most of the tests sit right on the edge of a rule, because that's where bugs hide. Fullness 29 should be hungry and 30 should not. Exactly 10 coins should be enough to buy food and 9 should not. A cat at 80 that gets fed should stop at 100 and not go up to 110. A test that only tried fullness 50 would never notice if someone typed `<=` instead of `<`.

I also wrote the expected answers as plain numbers taken from the spec, instead of reading them from `config.js`. If a test asked the config what food costs, and someone accidentally changed the price in the config, the code and the test would both be wrong in the same way and the test would still pass. When the test simply says "you should have 40 coins left," a wrong price shows up right away.

To find out whether the tests were actually any good, I broke the game on purpose, one line at a time, five times. I ran the tests after each change and then put the line back. I changed `<` to `<=` in the hunger rule, made buying food with exactly 10 coins fail, removed the 100 limit, and changed the bonus per fed cat from 5 to 4. The tests caught all four. The fifth change got past them. I deleted the line in `cats.js` that writes the new fullness back onto the cats after feeding. In the real game, that means you pay 10 coins and the cats don't eat, which is a pretty bad bug. Every test still passed, because the rule function itself was fine. The mistake was in the code that's supposed to use its answer.

That miss is why `game.test.js` exists. It loads the actual game files the same way the web page does, then checks that pressing Refill really takes the coins and really feeds the cats, and that customers really pay based on how full the cats are. After I added it, I broke the game the same five ways again, and this time every one of them made a test fail. My main takeaway is that testing small functions on their own isn't enough. You also need a couple of tests that check the pieces are connected.

I also wanted to see GitHub catch a bug for real. I pushed a commit that broke the hunger rule on purpose, and [the run on GitHub went red](https://github.com/0l-l/codycatcafe/actions/runs/44211276526). Then I pushed the fix and [it went green](https://github.com/0l-l/codycatcafe/actions/runs/44211285695). One thing I learned: you have to push the broken commit on its own first. If you push the broken commit and the fix together, GitHub only tests the newest one, and you never see the red run.

Last, I made a separate branch called `exp/payment-bug` where customers get the bonus for hungry cats instead of fed ones. I didn't change any test files there, and [three tests fail on GitHub](https://github.com/0l-l/codycatcafe/actions/runs/44211299183). I gave that branch to a fresh AI chat that knew nothing about the project and just said the tests were failing and to make them pass. It read the failing tests and the spec, figured out the code was wrong rather than the tests, and fixed the one bad line without touching the tests. Its fix was a little cleaner than the original code too, because it reused the hunger check instead of writing 30 a second time, so I brought that change back to the main testing branch, where [the tests pass](https://github.com/0l-l/codycatcafe/actions/runs/44213577621). The failure messages, like "expected 35 but got 20" under a test named after the rule, were clear enough that someone with no background could find the bug. That's a good sign the tests are doing their job.

The tests don't cover cats walking around, customer timers, seating, anything drawn on the screen, or stray cats, which aren't built yet. For those, open `index.html?speed=10` in a browser to make time run ten times faster, and watch. If I keep going, I'd test customer timing next by feeding the game fake seconds, write the stray-cat tests from the spec before writing the stray code, and repeat the break-it-on-purpose round after every big change, since it's the fastest way I found to discover what the tests are missing.
