# Testing Cozy Cat Café

To run the tests, open a terminal in this folder and type `node --test`. The tests live in the `tests/` folder, there's nothing to install, and any recent version of Node works (GitHub uses Node 26). Node finds every file that ends in `.test.js` and runs it. If everything is fine, the last lines say `pass 12` and `fail 0`. The same command also runs on GitHub every time someone pushes or opens a pull request. That's set up in `.github/workflows/tests.yml`. A red ✗ next to a commit on GitHub means a test broke. Click the ✗ to see which one.

The tests focus on the three rules that decide hunger and money in the game. A cat counts as hungry when its fullness is below 30. Refilling food costs 10 coins and gives every cat 30 more fullness, but never more than 100. A customer pays 20 coins, plus 5 for every cat at fullness 30 or above. I moved these rules into `rules.js` as small functions that take numbers and give back an answer. They don't touch the screen or the game state, which makes them easy to test, and `tests/rules.test.js` does exactly that.

Most of the tests sit right on the edge of a rule, because that's where bugs hide. Fullness 29 should be hungry and 30 should not. Exactly 10 coins should be enough to buy food and 9 should not. A cat at 80 that gets fed should stop at 100 and not go up to 110. A test that only tried fullness 50 would never notice if someone typed `<=` instead of `<`.

I also wrote the expected answers as plain numbers taken from the spec, instead of reading them from `config.js`. If a test asked the config what food costs, and someone accidentally changed the price in the config, the code and the test would both be wrong in the same way and the test would still pass. When the test simply says "you should have 40 coins left," a wrong price shows up right away.

To find out whether the tests were actually any good, I broke the game on purpose, one line at a time, five times. I ran the tests after each change and then put the line back. First, in `rules.js`, I changed the hunger check from `fullness < cfg.HUNGRY_BELOW` to `fullness <= cfg.HUNGRY_BELOW`, so a cat at exactly 30 would count as hungry. Second, I changed the money check from `coins < cfg.FOOD_COST` to `coins <= cfg.FOOD_COST`, so buying food with exactly 10 coins would fail. Third, I replaced `Math.min(cfg.FULLNESS_MAX, f + cfg.FOOD_AMOUNT)` with `f + cfg.FOOD_AMOUNT`, which removes the 100 limit. Fourth, in `config.js`, I changed `CUSTOMER_BONUS_PER_FED_CAT: 5` to `4`. The tests caught all four, with one or two failures each. The fifth change got past them. In `cats.js`, I commented out the line `state.cats.forEach((cat, i) => (cat.fullness = result.fullness[i]));`, which is what writes the new fullness back onto the cats after feeding. In the real game, that means you pay 10 coins and the cats don't eat, which is a pretty bad bug. All nine tests I had at that point still passed, because the rule function itself was fine. The mistake was in the code that's supposed to use its answer.

That miss is why `tests/game.test.js` exists. It loads the actual game files the same way the web page does, then checks that pressing Refill really takes the coins and really feeds the cats, and that customers really pay based on how full the cats are. After I added it, I broke the game the same five ways again, and this time every one of them made a test fail. The fifth one now fails with the cats' fullness still at `[0, 80]` when it should be `[30, 100]`. My main takeaway is that testing small functions on their own isn't enough. You also need a couple of tests that check the pieces are connected. The full diff and test output for every run are saved in `hw9-notes/`, which I kept out of the repo.

I also wanted to see GitHub catch a bug for real. I pushed commit `cc8eb3c`, which broke the hunger rule on purpose, and [the run on GitHub went red](https://github.com/0l-l/codycatcafe/actions/runs/44211276526) with 2 of 12 tests failing. Then I pushed the fix, `99f93f5`, and [it went green](https://github.com/0l-l/codycatcafe/actions/runs/44211285695). One thing I learned: you have to push the broken commit on its own first. If you push the broken commit and the fix together, GitHub only tests the newest one, and you never see the red run.

Last, I made a separate branch called `exp/payment-bug`, starting from `99f93f5`. On it, commit `b21b76c` makes customers get the bonus for hungry cats instead of fed ones. I didn't change any test files there, and [three tests fail on GitHub](https://github.com/0l-l/codycatcafe/actions/runs/44211299183). Then I opened a fresh AI chat that knew nothing about the project and sent it exactly this: "Please work on branchexp/payment-bug in https://github.com/0l-l/codycatcafe. The test suite is failing. Make it pass." It answered that `payment()` was giving the bonus to cats below the hunger line, while the spec says the bonus is for cats at 30 or higher. It also noticed that the commit message called the bug deliberate and said the tests were unchanged, so it fixed the code and left the tests alone. It reported 3 failures before the fix and all 12 passing after. Its push to GitHub failed because that chat didn't have access to my repo, so I checked the change myself and got the same 12 passes. This was its whole diff, one line in `rules.js`:

```diff
-    const fedCats = fullnessList.filter((f) => f < cfg.HUNGRY_BELOW).length;
+    const fedCats = fullnessList.filter((f) => !isHungry(f)).length;
```

Its fix was a little cleaner than my original code, because it reused the hunger check instead of writing 30 a second time. The main branch never had the bug, so I brought only that improvement back to `hw9-tests` as commit `2729446`, where [the tests pass](https://github.com/0l-l/codycatcafe/actions/runs/44213577621). The failure messages, like "expected 35 but got 20" under a test named after the rule, were clear enough that someone with no background could find the bug, which is a good sign the tests are doing their job.

The tests don't cover cats walking around, customer timers, seating, anything drawn on the screen, or stray cats, which aren't built yet. For those, open `index.html?speed=10` in a browser to make time run ten times faster, and watch. If I keep going, I'd test customer timing next by feeding the game fake seconds, and I'd write the stray-cat tests from the spec before writing the stray code. I'd also repeat the break-it-on-purpose round after every big change, since it's the fastest way I found to discover what the tests are missing.
